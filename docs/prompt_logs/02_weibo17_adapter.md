# Prompt 链 02：Weibo17 适配器与标签口径核验

> 日期：2026-10-03  
> 负责人：参赛者本人  
> 关联提交：`a0efa63`、`cfda90b`、`bd9722a`  
> 核心目标：从本地 `weibo.zip` 独立构建统一 JSONL，并保证文件名、划分、标签方向和图文配对正确。

---

## 1. 初始意图

### 1.1 原始 Prompt（本人关键原句，按对话留痕整理）

```text
Weibo17 是什么？
它在哪里？
这个是不是 Weibo17？
可以，先验证一下，如果可以，我就用了。
那就不再等待许可回复，接下来干什么？
只用 Weibo17 就行。
```

### 1.2 真实诉求

- 确认下载到的 `weibo.zip` 是否就是 Weibo17/EANN 数据；
- 不能只凭目录名判断，要核对官方 pickle、数量、标签和图片；
- 数据只保存在本地，不重新分发；
- 在没有明确许可证回复的情况下，走公开研究数据路线，但保留风险披露；
- 不把 `9,527`、`9,411` 和官方评测 `7,723` 混在一起。

---

## 2. AI 建议

AI 建议先做只读核验，再写适配器：

1. 计算归档大小和 SHA-256，检查 ZIP 中央目录和条目 CRC；
2. 确认三个官方划分文件：
   - `train_id.pickle`
   - `validate_id.pickle`
   - `test_id.pickle`
3. 统计三个 pickle 的 ID 数量、交集和重复；
4. 按官方 ID 从文本和图片文件中取出样本，单独统计标签；
5. 用少量样本人工检查图文是否对应；
6. 输出本地 JSONL 和 manifest，原始数据不入库；
7. 在文档中明确：公开研究数据路线不等于已获得额外授权，不重新分发。

### AI 建议中需要人工修正的点

- AI 最初按常见命名写成了 `val_id.pickle`；
- 实际官方归档使用 `validate_id.pickle`；
- 如果不以真实文件名为准，适配器会在数据构建阶段直接失败。

---

## 3. 人工决策

### 采纳

- 采纳“先核验、后适配”；
- 采纳官方三个 pickle 作为唯一划分；
- 采纳 `0 = real/non-rumor`、`1 = fake/rumor` 的标签契约；
- 采纳 manifest 审计文件和本地图片目录；
- 采纳公开研究数据路线，不等待许可证回复，但不声称已获授权；
- 采纳“不提交原始正文、完整 ID、图片”的合规边界。

### 不采纳

| 建议 | 不采纳原因 |
|---|---|
| 根据四个文本文件名自行划分 train/val/test | 这些文件不是官方划分边界 |
| 用 `9,527` 或 `9,411` 替换官方 `7,723` 评测集 | 口径不同，会造成结果不可比 |
| 把完整 ID 列表写进文档作为“证据” | 可能造成数据再分发和隐私风险 |
| 在项目里内置自动下载脚本 | 不应提供绕过官方渠道的下载方式 |
| 用“已获授权”描述数据权利 | 当前没有许可证闭环，不能夸大 |

## 4. 真实 Bug 与修复

### Bug 1：官方划分文件名不一致

- **现象**：适配器按 `val_id.pickle` 查找失败；
- **根因**：官方归档实际文件名为 `validate_id.pickle`；
- **修复**：以归档真实文件名为准，增加文件存在性测试；
- **验证**：`tests/test_weibo17_adapter.py` 覆盖 `validate_id.pickle` 路径；
- **关联**：`cfda90b`。

### Bug 2：标签方向不能靠猜

- **现象**：候选标签映射可能把 fake/real 方向写反；
- **根因**：数据说明、代码和文本池中的标签统计容易混淆；
- **修复**：固定标签契约为 `0 = real/non-rumor`、`1 = fake/rumor`，增加契约测试；
- **验证**：`tests/test_label_contract.py`；
- **关联**：`a0efa63`。

### Bug 3：本地图片名和文本 ID 的配对问题

- **现象**：文本存在但图片缺失或图片名复用，可能让样本错配；
- **根因**：不能在未检查的情况下假定文件名天然一一对应；
- **修复**：在适配器中保留图文配对检查、缺失数统计和 manifest；
- **验证**：适配器测试覆盖配对和缺失路径。
